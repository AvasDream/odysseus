Findings

Scheduled email is delivered before the row is claimed/marked sent — crash or dual-driver causes duplicate sendMedium real

Severity
Medium — at-most-once delivery invariant violated by normal operational events; impact bounded to duplicate delivery of an email the owner already intended to send.
Confidence
Confirmed by trace. Preconditions: a scheduled email in scheduled_emails with status='pending' and send_at <= now. Then EITHER (A) the server is killed/restarted during the SMTP round-trip — after _send_smtp_message returns (1057) but before the UPDATE at 1070 commits — under default config (ODYSSEUS_INPROCESS_POLLERS on); next tick re-delivers. OR (B) operator runs both the in-process poller and a cron odysseus-mail poll-scheduled and both passes overlap. No attacker required.
Location
routes/email_pollers.py:1010-1085 (_scheduled_poll_once); driver 1088-1101
Invariant violated
A queued scheduled email must be delivered at-most-once: the row must be atomically claimed (status flipped out of 'pending') BEFORE the irreversible SMTP send, so re-entry can never re-deliver it. Here the claim (UPDATE status='sent', 1070) happens AFTER the send succeeds (1057), and the initial SELECT (1010-1014) does not claim the rows.
Why it matters
The same email is sent twice (or N times) to all To/Cc/Bcc recipients. (a) crash/restart in the window between SMTP delivery (1057) and the status UPDATE (1070) leaves the row still 'pending' and due, so it is re-selected and re-delivered; (b) two drivers both SELECT the same pending row and both deliver before either flips status. The docstring (1122-1123) acknowledges (b) but relies on an env flag instead of an atomic claim.
Trigger
No attacker needed; normal operational events (deploy, OOM, crash, SIGKILL) or operator misconfiguration. Affects any owner with scheduled/agent-approved sends. (A) needs no misconfiguration; (B) needs the dual-driver setup.
Fix direction
Atomically claim before sending: UPDATE scheduled_emails SET status='sending' WHERE id=? AND status='pending' and proceed only if rowcount==1; on success set 'sent', on failure set 'failed'/'pending' with bounded retry. Makes re-entry idempotent and closes both the crash window and the dual-driver race.
Root cause

Assumptions made

  • stdlib email uses default compat32 policy here (no policy= override), so as_string()/as_bytes() raises HeaderParseError on header values with embedded newlines — verified empirically.
  • imaplib rejects CRLF inside command arguments, so folder/uid/search CRLF cannot inject extra IMAP commands.
  • Each multi-user deployment assigns every user a non-empty owner; owner=='' denotes unconfigured single-user mode where cross-tenant concerns are vacuous.
  • uuid4 tokens for compose uploads are unguessable.
  • _load_or_create_key() returns a stable per-deployment secret so HMAC-signed OAuth state cannot be forged.
