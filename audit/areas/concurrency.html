CancelledError in _cached() owner leaks an unresolved pending future, permanently poisoning the shared singleflight cache keyMedium real

Severity
Medium — durable (process-lifetime) cross-user availability loss of shared scheduled-task fetches, triggerable by a non-admin.
Confidence
Confirmed by trace. Preconditions: two or more users have check-in/digest tasks touching the same shared integration (same Miniflux base_url, or same MCP server snapshot tool); one user's task is the singleflight owner suspended inside _cached at await fetch() (httpx GET up to ~10s, or mcp.call_tool) or at the line-85 lock; that task is cancelled (most directly via the owning non-admin user's POST /tasks/{task_id}/stop). No special privilege required.
Location
src/task_scheduler.py:60-94 (owner 83-94); callers :1302, :1339; cancel source :2089-2102
Invariant violated
The owner of an in-flight singleflight key must ALWAYS remove _shared_cache_pending[key] and resolve the future before exiting on every path. except Exception does not catch asyncio.CancelledError (a BaseException), so cleanup is bypassed.
Why it matters
If the owner is cancelled at await fetch() (84) or the success-path lock (85), neither 87/88 nor 92/93 runs. The pending dict keeps an unresolved Future and the cache entry is never written. (1) Every waiter at await pending (82) hangs forever (lost wakeup). (2) Every future caller for that key re-reads the stale future (71-74) and also hangs. Keys are process-global and shared across users, so one user stopping their own task can hang other users' scheduled tasks until process restart.
Trigger
A scheduled check-in/digest task becomes the singleflight owner and suspends inside await fetch(); the owning non-admin user clicks Stop → stop_task() → handle.cancel() (:2093) delivers CancelledError; cleanup is skipped; the key is poisoned for everyone. Triggerable by any non-admin task owner.
Fix direction
Wrap the owner body in try/except BaseException or a finally that always pops the key and, if the future is not done, calls pending.cancel() (or set_exception) so waiters wake; re-raise CancelledError.

Orphaned tool-execution task (running bash/python subprocess) on agent-turn cancellationLow real

Severity
Low — owner-triggered only, bounded by the 3600s tool timeout, side effects owner-initiated; cancellation-correctness / resource-leak, not a security-boundary bug.
Confidence
Confirmed by trace (empirically reproduced: detached _tool_task was NOT cancelled, ran to completion). Preconditions: session owner runs a long bash/python tool, then either (a) presses Stop on a normal/detached run (agent_runs.stop → task.cancel → agen.aclose), or (b) disconnects the SSE client in compare_mode, while stream_agent_loop is suspended at :3127 or :3133.
Location
src/agent_loop.py:3104-3133
Invariant violated
A child task owning external resources (a bash/python subprocess via execute_tool_block) must be cancelled/awaited on every parent exit path, including GeneratorExit on the parent async generator. Awaiting a Task does not cancel it when the awaiter is cancelled.
Why it matters
If the generator is cancelled while suspended at await _progress_q.get() (3127) or await _tool_task (3133), _tool_task is not cancelled. The orphaned _run_tool keeps the subprocess running up to the 3600s timeout with no consumer, leaking CPU/process resources and partial side effects after the user pressed Stop.
Trigger
Long bash/python tool in flight; user presses Stop on a normal run, or SSE client disconnects in compare_mode. Session owner (any user). In default detached mode a bare SSE disconnect does NOT cancel the run by design.
Fix direction
Wrap the drain loop and await _tool_task in try/finally; in finally, if not _tool_task.done() cancel and await it (suppressing CancelledError) so the subprocess is torn down with the turn.

Cancelled background HTTP MCP connect leaks its AsyncExitStack (transport/subprocess)Low real

Severity
Low — admin-only action within the trusted boundary, finite per-occurrence leak, no privilege/auth/secret-leak impact.
Confidence
Confirmed by trace. Preconditions: admin connects an HTTP/OAuth MCP server (background connect in flight during OAuth discovery/DCR/slow network), then calls disconnect_server / deletes the server (or reconnect churn) while _connect_http is suspended at line 343 (streamablehttp_client) or 345 (ClientSession) — before line 358 stores the stack.
Location
src/mcp_manager.py:325-378 (_connect_http), :380-404 (disconnect_server, cancel at 384-386)
Invariant violated
disconnect_server must guarantee the transport/exit-stack is closed exactly once. The only aclose() path is via disconnect_server popping self._stacks; _connect_http catches only except Exception (375), so a CancelledError at the pending await (343/345) before the stack is stored (358) leaves the local AsyncExitStack (httpx transport + anyio task group) never closed. The secondary "re-population" claim does NOT trigger (no interleaving await between 358 and completion) and was excluded.
Why it matters
disconnect_server cancels the task (386) but does not await it, then pops _stacks (None at that moment). The in-flight stack's transport/ClientSession is never aclose()'d → leaked httpx connection / anyio task group, with nothing to later clean it up.
Trigger
Admin connects an HTTP/OAuth MCP server and disconnects/deletes it (or reconnect churn) before the connect completes. Admin-only, within the trusted boundary; reported as a cancellation-safety resource leak, not a privilege issue.
Fix direction
In _connect_http, use try/finally (or except BaseException) to aclose() the stack on cancellation; in disconnect_server, await the cancelled connect task (suppressing CancelledError) before popping/closing state.

Systemic pattern

Bare except Exception as the cleanup path on a cancellable coroutine. All three findings share one root: external resources (a shared future, a subprocess, an HTTP transport stack) are released only inside except Exception / success branches, never in a finally or except BaseException. Because asyncio.CancelledError derives from BaseException, a Stop/disconnect/disconnect-server delivered at an inner await skips cleanup entirely, leaving poisoned shared state or leaked resources. The structural fix is the same in each case: move release into a finally (or catch BaseException) and re-raise.

Assumptions made

  • asyncio.CancelledError subclasses BaseException (Python 3.8+), so except Exception does not catch it — core premise of the _cached and MCP-connect findings.
  • stop_task → handle.cancel() delivers CancelledError into the running _execute_task coroutine at its current await point.
  • _cached callers (_fetch_miniflux, _call_mcp) perform real awaits (HTTP/MCP) long enough for a cancellation to land mid-fetch.
  • Awaiting a Task and then being cancelled does NOT propagate cancellation into the awaited Task — basis for the agent_loop orphan finding.

N/A scope areas

  • Pure prompt-injection wrapper bypass and authz/IDOR are outside this concurrency lens (email_pollers calendar extraction wraps untrusted email as data and is owner-scoped; not a concurrency issue).
  • Admin-intended powerful capabilities (shell, MCP management, model serving) are by-design per THREAT_MODEL — the MCP-connect leak is reported only as a cancellation-safety resource leak.
