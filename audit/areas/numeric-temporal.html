Location
src/task_scheduler.py:1205-1227 (window build + strip); src/task_scheduler.py:255-289 (_digest_windows / _checkin_calendar_events); re-print at src/task_scheduler.py:1242
Invariant violated
When comparing datetimes against DB rows, both sides must share a reference frame. CalendarEvent.dtstart for tz-carrying events is stored as naive UTC (caldav_sync._to_utc_naive / calendar_routes._parse_dt_pair convert tz-aware → UTC then strip tzinfo). The window boundaries are built from now, which when a task timezone is set is tz-aware LOCAL time (line 1205). Stripping tzinfo with .replace(tzinfo=None) yields naive LOCAL wall-clock, NOT naive UTC, so the window is offset from the stored UTC instants by the zone's UTC offset.
Why it matters
For any owner whose CrewMember.timezone is non-UTC, the "today/tomorrow", "this week" and "next_30_days" check-in buckets shift up to +/-14h relative to stored UTC event times. Events near a bucket boundary are silently dropped or pulled into the wrong bucket; for zones behind UTC (the Americas) the early part of "today" is missed and late events of the prior day leak in. The re-printed event times (line 1242 strftime) are also raw UTC, compounding the misrepresentation. No cross-tenant leak — query is owner-scoped — so a correctness/UX defect, not a privilege/data-exposure bug.
Trigger
A non-admin or admin owner sets a non-UTC timezone on their default-assistant CrewMember and runs a "...check-in" scheduled LLM task (is_checkin path). Fires every time that task executes. Triggerable by the task owner only.
Fix direction
Convert the window bounds to UTC before stripping: _s = start.astimezone(timezone.utc).replace(tzinfo=None) if start.tzinfo else start (and same for _e), instead of dropping the offset. Equivalently, build _digest_windows from a naive-UTC now for the DB query while keeping the tz-aware now only for the human-readable time_str.
